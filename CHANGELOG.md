# AIBL Installer changes

## 2026-09-25

- **No route builds a workbench from the retired private Essentials course any more.** Students who set up through the older one-line launchers between 09-14 and 09-16 got a workbench made from `aibuild-lab/agent-essentials` (Hunter's retired in-workbench mission course: `/aibl-teach`, no `aibl-enroll`, no `.agents/skills`), because `start.sh` and `start.ps1` ran `course_setup.py --course agent-essentials` when no course was given, and `course_setup.py` created from `hub.template`. Now:
  - `start.sh` and `start.ps1` without a reviewed pin run `scripts/hub_setup.py`, the same script `SETUP-PROMPT.md` step 8 runs, so the result is the public-template workbench. They sign in to GitHub first only when `gh` reports no sign-in (exit 4), as `course_setup.py` did. A course argument without a pin is noted, not installed; programs join later through `aibl-enroll`. A retained installer too old to have `hub_setup.py` stops with a message instead of falling back to its own `course_setup.py`, which would still use the private template.
  - `scripts/course_setup.py` with no family lock and no distribution lock hands off to `hub_setup.py` (`--plan` shows that route with no effects). `hub.template` is gone from `course-options.json`; `resolve()` reads `hub.public_template`, and the create step refuses any template listed as retired.
  - Unchanged: the paste route (`SETUP-PROMPT.md`, `hub_setup.py`), `UPDATE-PROMPT.md`, enrollment, the family and standalone lock routes, and the pinned course-distribution route. The pinned route still reads the `agent-essentials` publisher and downloads its pinned release from `aibuild-lab/agent-essentials`, so that program entry keeps its publisher. The `agent-essentials` program id stays: it is the site ledger slug.

## 2026-09-24

- **Codex guard launches on Windows accounts whose folder name has a space.** A Windows student on codex-cli 0.156.1 (account folder `C:\Users\<First Last>`) saw `hook: PreToolUse Failed` and `hook: PostToolUse Failed`, and Codex ran `cat .env` anyway. `refresh-guard.mjs` registered each Codex launcher as a bare path, on the belief that Codex does not shell-parse hook commands. It does: current Codex runs them through the session's shell, which is Windows PowerShell on a default install. PowerShell split the path at the space, so the hook could not launch, and Codex fails open when a hook fails. Quoting the path does not help, because PowerShell prints a quoted string instead of running it. On Windows the command is now `cmd /d /c "<launcher>"`, which launches under `cmd`, Windows PowerShell and PowerShell 7, with or without a space. `--check` names the old form and `--codex` repairs it in place. `refresh-guard.test.mjs` now launches the registered commands the way Codex does, through every available shell, from an account folder with a space, and pins the old form's failure. Against the previous `refresh-guard.mjs`, those new checks fail (4 of them); against this one, all pass. macOS keeps the bare path, since account folders there cannot contain a space. Codex students need to re-run `refresh-guard.mjs --codex` and trust the hooks again.
- **Secrets guard: Windows shells are unwrapped, and the Windows read verbs apply under Codex's `Bash` label.** A Windows student on Codex CLI 0.156.1 reported that the Codex canary (`cat .env`) ran instead of being refused, and that Codex showed it as `pwsh.exe -Command 'cat .env'`. Replayed against the pinned guard, every Windows-wrapped form was allowed: `pwsh`/`powershell -Command`, `-EncodedCommand`, Windows PowerShell's positional command, `cmd /c`, and `Invoke-Expression`. `secrets-guard.js` now unwraps each one and inspects the inner command recursively, like `bash -c`. It also closes camp-hq **W-#234**. Codex on Windows labels its PowerShell shell `Bash`, so `type .env`, `Get-Content .env` and `Get-ChildItem Env:` used to pass. The Windows readers and `Env:` rules now apply under either tool name. W-#234's local compensating hook (`codex-windows-verb-guard`) can be retired on machines that have it. The test table gains 37 cases, 26 deny and 11 allow. Replaying 24,084 unique real Bash and PowerShell commands through the old and new guard changed exactly one verdict: a heredoc commit body that named `[System.Environment]::GetEnvironmentVariables()` in prose. Under the Bash label, the two `Env:` text rules now match only where a command can begin, and that case is pinned as an allow. Manifest re-pinned for `secrets-guard.js` only. Not fixable here, now documented in `hooks/README.md`: Codex on Windows sometimes does not invoke `PreToolUse` at all ([openai/codex#24453](https://github.com/openai/codex/issues/24453)). When that happens, no guard change helps, and the canary fails even though the hooks are trusted.
- Secrets guard: four false-alarm fixes from a live database cutover. Guard files and manifest change together (`ref` aibl-installer-2026-09-24-secrets-guard-narrow-false-positives).
  - **`--plain` keys on the binary.** The deny fires only when a secret-store CLI (infisical, op, vault, doppler, bw, chamber, sops, gopass, pass, teller) runs with `--plain`, including wrapped forms (`bash -c`, `ssh`, `sudo`, `op run --`) and payloads the tokenizer does not unwrap (`python3 -c`, `node -e`, `xargs`). Every `systemctl ... --plain` listing is allowed; this replaces the exact-string exception from #33.
  - **Names-only environment listing, NUL-record form only.** `env -0` (or `env --null`) piped directly into `cut -z -d= -f1` is allowed: each variable is one record, so a multi-line value cannot spill. The newline form `env | cut -d= -f1` stays denied, with or without `-s`, because `cut` prints a line without `=` in full and base64 lines can contain `=`. Other fields, ranges, `--complement`, other delimiters, and any stage between `env` and `cut` stay denied.
  - **`docker buildx inspect <builder>` is allowed.** It describes a build instance, not a container. Container, image, and `buildx imagetools` inspect stay denied.
  - **Tripwire skips DSN template slots.** The "DB URL with password" pattern leaves `%s`, `%(x)s`, `$VAR`, `${VAR}`, `{x}`, `<x>`, and `***` alone. Real passwords are still redacted.
- **Codex guard proof is headless, and it can tell a failure's cause.** `SETUP-PROMPT.md` step 7 used to have the student type `cat .env` into the same interactive Codex session, in their home folder. If the command ran, the only explanation offered was "the trust step was skipped", so a Windows student whose hooks were trusted but not called went round a re-trust loop with no exit. Now the student only grants trust in the interactive screen. The assistant then proves it with a fresh `codex exec` in an empty `aibl-guard-test` folder, so no real `.env` is in reach and Windows' home-folder failure for `codex exec` is avoided. Plain `codex exec` prints a `hook:` line for every hook call, which separates the outcomes. `hook: PreToolUse Blocked` with the `[Codex secrets-guard adapter]` tag is a pass. `Completed` means the guard ran and allowed the command, which is a guard defect. No `hook:` line means Codex never called the hook: one re-trust, then stop. When it is not proven, the student is told plainly that finishing setup is safe but no real key goes into Codex until the guard passes, and continues. Only a guard problem the team can fix (Completed, Failed after the repair, or a Mac with no hook call) asks the student to post the output; a known Codex limit (the model would not test, or Windows Codex never called the hook) asks for no report, so it does not become a support thread nobody can act on. The wording names no program, because the installer also serves programs that use keys; step 10 says "installed, not yet proven in Codex". `hooks/README.md` drops the claim that headless Codex never runs hooks. It cannot grant trust, but it honors trust already granted (verified on codex-cli 0.154.0, Windows 11, with blocked, allowed and no-hook runs). Rule 11 names the test folder. Both commands were run live and blocked with the adapter tag: Windows on codex-cli 0.154.0 and on 0.156.1 (a student, account folder with a space), and macOS on codex-cli 0.147.0. The stronger prompt wording also works with `gpt-5.6-luna` at low effort, which declines the plain wording.

## 2026-09-19

- Six fixes from the first real Mac run of the paste route (a team member on a Homebrew machine, 09-19). None changes the install flow or a pinned guard file.
  - **Guard proof cannot false-pass.** `SETUP-PROMPT.md` step 7 frames the headless test as a deliberate test of the hook, so the model attempts `cat .env` instead of declining on its own judgment before the hook runs. The only pass signal is now the literal `[secrets-guard hook]` tag the guard appends to every refusal; a model refusal without it is named as a fail. The diagnostic check is scoped to the chosen app (`--check --claude`), so a Claude-only student is not told a Codex guard is missing.
  - **A failed tool names its own error.** `course_setup.command()` now appends the tool's last stderr (or stdout) lines to the paused message with the exit code, instead of only our classification. The run that prompted this failed once with "check the network" on a GitHub-side hiccup and left nothing to diagnose; the classification was right, the evidence was hidden. "Rerun the same launcher" becomes "run the same command again".
  - **Any Claude Code install counts.** Step 3 detects the native installer, Homebrew (`/opt/homebrew/bin/claude`, `/usr/local/bin/claude`) and npm locations; 4.4 and 5.3 install only when none was found, so a Homebrew Claude never gets a second copy; the proof runs the `claude` that answered `--version` in 4.6 or 5.5.
  - **Hook commands use the stable Node launcher.** `refresh-guard.mjs` picks `/opt/homebrew/bin/node`, `/usr/local/bin/node` or `C:\Program Files\nodejs\node.exe` when it resolves to the running binary, and passes it to `install.mjs` through the `CLAUDE_HOOK_NODE` seam that file already had, and to the AWS supplements and the Codex launcher. `process.execPath` alone resolves Homebrew's symlink to the versioned Cellar path, which `brew upgrade node` deletes; Claude Code treats a hook that cannot launch as a non-blocking error, so the guard would have switched off in silence. The install output now names the Node path it wrote. Importing the module no longer runs the installer (`pickStableNode` is unit-tested; every written command is asserted to use the picked path).
  - **A "No folder" session continues.** Step 1.5 accepts the home folder or no folder open, since every path in the procedure is absolute; it still stops for a project or cloud-synced folder and says why (the workbench created inside the home folder is already trusted when opened later).
  - **No hunt for a "core version".** Step 10 dropped the phrase; `hub_setup.py` reads the template's `.aibl/template.json` version into the receipt (`template.version`, `null` when the template ships no stamp) and step 8 tells the assistant where to read it.

## 2026-09-11

- Enrollment leaves the installer. The installer builds the Essentials hub for everyone and never asks which program a student is in: `SETUP-PROMPT.md` step 2 drops the program question, step 8 always runs `--course agent-essentials`, `START-HERE.md` and both terminal launchers follow, and the "bundled program not yet" pause is gone because the installer checks only the template. New `scripts/enroll.py` runs later, inside the workbench: it refreshes this checkout, reads the registry, asks GitHub which program repositories the signed-in account can read (a 404 is "not invited"; sign-in and network failures stop plainly and are never read as absence), reports a bundled program as "included, invitation pending" rather than missing, shows the list, asks before doing anything, records the decision in `.aibl/enroll.json`, and names each program's adoption skill. It never touches release pins; adoption stays with `aibl-adopt-workforce`. Re-runnable: an installed program (`.aibl/installed-<product>.json`) is left alone. The registry gains `adopt_skill` per program (`null` means no adoption route yet, so the Lab reports clone-beside for now); `menu` is kept for tooling but the installer no longer reads it. An explicit course argument remains for pinned cohort setups. `tests/test_enroll.py` covers joined, not invited, included-pending, installed, decline, `--yes`, `--check`, `--program`, signed-out, network-down and the CLI. Why: chapter 2 of Essentials has no branch point, every setup recording is program-agnostic, and the ship-day team grants no longer have to precede install.
- Secrets guard for both apps, canonical here. `hooks/refresh-guard.mjs` and the Codex and AWS adapters are ported from `agent-native-os` (its `scripts/refresh-guard.mjs`, `codex-secrets-guard.mjs`, `codex-secrets-tripwire.mjs`, `aws-credential-*.mjs`, and trust manifest), reading the canonical files from this directory instead of downloading a tag, LF-normalized so a Windows checkout installs the exact pinned bytes. Rolled in: the Stripe live-key rule (workshop-installer #17) and the Codex trust-step guidance (agent-native-os #89). The manifest is recomputed for the reviewed bytes; `hooks/manifest.test.mjs` fails CI on drift and `hooks/manifest-regen.mjs` rewrites it inside a reviewed change. The setup prompt installs both guards with one command and proves each by behavior: a headless refusal for Claude, and for Codex the interactive trust screen ("Trust all and continue") followed by a refused `cat .env`, because headless Codex never runs hooks.
- App-first entry. `SETUP-PROMPT.md` returns, rewritten for the program route and both apps: the student opens the Claude or Codex app on their home folder and pastes one prompt; the app audits, explains, installs only what is missing (Git, GitHub CLI, Python, Node, the app's command-line twin, the secrets guard), guides the two browser sign-ins, then runs `course_setup.py --harness <claude|codex> --no-launch` to create the workbench the tested way, and tells the student how to open it in the app. `START-HERE.md` leads with that route; the terminal launchers remain as the fallback and accept `AIBL_HARNESS` / `-Harness`. `course_setup.py` gains `--harness`, Node in the floor, Codex sign-in via `codex login status`, and never hands Codex a slash command. The prompt joins the pinned file set. Codex secrets guard: the prompt installs it when `hooks/codex-secrets-guard.mjs` is present and says so plainly when it is not yet.
- Program registry. `course-options.json` is now `aibl.program-registry/v1`: one line per program with the site ledger's ids (`agent-essentials`, `agent-workforce`, `the-lab`), the publisher repository, what each program requires (checked strictly) and includes (checked softly and reported as found or not yet). The menu is generated from it and asked by `course_setup.py` after tools are ready; the launchers no longer carry a hard-coded menu. The Lab is a program of its own and is included with Agent Workforce. The pinned course id follows the registry (`agent-workforce`); release product ids are unchanged.
- Seeded `aibuild-lab/aibl-installer` from `workshop-installer` at 64130d9 with full history. Removed the legacy Agent Native OS route (install.mjs, install.sh, install.ps1, SETUP-PROMPT.md, MANUAL-INSTALL.md, the migration and repo-prep scripts, their test, and the generated OpenWiki pages); it stays in `workshop-installer`, frozen. The course menu is Essentials and Agent Workforce. Every installer reference now names `aibuild-lab/aibl-installer`, so any existing frozen distribution lock is invalid by design and must be regenerated.
